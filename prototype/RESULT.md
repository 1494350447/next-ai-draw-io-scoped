## 1. 越界率 0

两条独立的防线，各自都被测试覆盖：

- **意图层**：穷举每个样例、每种选择下的**每一个作用域外 cell**，对它发 `style` / `move` / `delete` / `update`
  四类 op，共 444 个，**全部被拒绝**（`guardOps` 整批拒绝，不部分应用）。
- **结果层**：36 个组合命令逐一执行后，重新解析改动前后 XML 算真实改动集合，
  必须 ⊆ `writable`；同时逐字节核对未改动元素。

结果层还专门覆盖了三种"看起来像但其实是越界"的场景：把作用域外元素挪进作用域（改 parent）、
新增/删除元素、以及"重新排版产生的空白不算改动"（避免误报）。

## 2. 未选中元素逐字节不变

实现基础是**保偏移解析**：写操作只替换"某个属性的值区间"，不重新序列化。
所以未选中的元素是字面上"没被碰过"，而不是"重新生成后内容相同"。

## 3. token 占比（实测）

```

small-flow cell= 11 roots=[10,11]     →    387/   652 = 59%（可改 251+邻域  94+骨架 0+约束 43）
small-flow cell= 11 roots=[14]        →    240/   652 = 37%（可改  72+邻域 126+骨架 0+约束 43）

aws-demo   cell= 11 roots=[2]         →    842/  1067 = 79%（可改 743+邻域  56+骨架 0+约束 43）
aws-demo   cell= 11 roots=[2,7]       →    934/  1067 = 88%（可改 845+邻域  46+骨架 0+约束 43）
aws-demo   cell= 11 roots=[8]         →    258/  1067 = 24%（可改  87+邻域  77+骨架 52+约束 43）

synth-200  cell=401 roots=[v7,v8,v9]  →    652/ 21955 =  3.0%（骨架逐条枚举的版本是 2554 = 11.6%）
```

（token 为粗估：ASCII 4 字符 ≈ 1 token，CJK 1 字符 ≈ 1 token。）

**产品结论（重要，别被"3%"误导）**：

1. **作用域编辑的价值从中等图开始，小图没有 token 收益。** 10~20 个 cell 的图上"脚手架"
   （约束行 43 + 邻域 + 骨架）本身就占相当比例，甚至超过可改部分 —— 这时省 token 不是卖点，
   **"只改我选中的、其余不动"的可控性**才是。
2. **占比由"选中了什么"主导，而不是由图多大主导。** `aws-demo roots=[2]`（选中 AWS Cloud 顶层容器）
   占 88% —— 因为选中容器等于把它的子孙全纳入 `writable`，此时"作用域"本来就≈全图。
   所以产品上要给出**"这次会改 18 个元素"的即时反馈**，而不是让用户以为"选了一个框所以只改一点"。
3. **约束行是固定开销**：43 token。将来接模型时它必须留在系统提示里而不是每次重发。

## 4. 过程中发现并修掉的缺陷：邻域层没有边界收敛

**现象**：验收 3 一开始就失败 —— `compact` 与 `full` 两种骨架渲染出的 token **完全相等**（都是 5055），
并且 `skeleton` 是**空的**。

**根因**：`context.siblings`（只读邻域的"同层邻居"）没有上限。draw.io 最常见的形态是**所有元素 `parent="1"`**，
此时"同层邻居"就是**除选区外的整张图**。于是 200 个顶点的图上，邻域塞进 392 个元素，
`inContext` 把骨架挤成空集 —— 作用域退化回"把整张图发出去"，而且 compact 模式失去意义。

有容器层级的图（aws-demo）看不出来，是因为兄弟数量天然少 —— **所以这条只有在扁平图上才会暴露**，
而扁平图恰恰是真实用户最常见的画法。

**修复**（`src/scope.mjs`）：

- 邻域按**几何邻近度**排序（离选区包围盒中心由近到远；无几何的边/未布局元素排最后），截断到 12 个。
- 被截断者**降级进 skeleton**，不是丢弃 —— compact 渲染只计数量（"其余 N 个节点、M 条边未列出"），
  容器仍**逐条**列出（模型要选 `add` 的 parent，必须能拿到容器 id）。
- 暴露 `context.siblingsTotal/siblingsOmitted` 与 `warnings`，并把 `estimate.breakdown`
  做成**分段 token 账单**（可改/邻域/骨架/约束），因为优化作用域唯一能下手的地方就是"哪一段吃掉了预算"。

**效果**：synth-200 从 **5055（23.0%）→ 652（3.0%）**，逐条枚举骨架的版本是 2554（11.6%）
—— 两种模式终于拉开差距。回归测试：`test/scope.test.mjs` 的"邻域有界"两条。

## 5.2 预览交互：点空白清空 + 框选语义

原先只支持"点元素切换"，**单击空白没有任何反应**（拖拽才会框选），这与直觉不符。现已按 draw.io 的习惯补齐
（`public/app.mjs` 的 pointerdown/move/up）：

| 操作 | 结果 |
| --- | --- |
| 点空白 | 清空选择 |
| 点元素 / 点它的文字标签 | 切换该元素 |
| 拖拽 | 框选（**替换**选择） |
| Shift + 拖拽 | 框选并加选 |
| `Esc` | 清空 |

浏览器回归（`smoke-prototype.mjs`，7 条断言全过）：

```
点空白清空: 通过        点元素切换: 通过      点标签=点元素: 通过    Esc 清空: 通过
拖拽框选: 通过          框选替换(不按 Shift): 通过                 Shift 加选: 通过
```

三个实现细节，都不是想当然：

1. **"点"与"拖"必须用位移阈值（4px）区分**，否则手一抖就变成框出一个 0×0 的空框；且点击要**等 pointerup 才生效**，
   这样"从元素上按下也能拖框选"（在 mousedown 时切换选中就没法拖了）。
2. **文字标签也要带 `data-id`**：否则点元素的文字会被当成"点空白"，把辛苦选好的作用域清掉。
3. **命中遵循叠放顺序**（和 draw.io 一致，不做穿透）。第一次写这条测试时踩到了：`small-flow` 里的 `13` 是个
   560×320 的大矩形，包住 `10`/`11`/`12` 却没有真的当它们的父容器，后画所以盖在最上层 —— 点 `10` 的中心
   实际命中的是 `13`。测试因此改成"按屏幕上最上层是谁来断言"，而不是"我点的是哪个矩形"。

## 5.3 改动高亮 + 改动账本 + 撤销本轮

"作用域编辑"要让用户敢用，光有"能不能改"还不够，必须回答"**到底改了什么**"。三件套：

| 件 | 实现 | 为什么这么做 |
| --- | --- | --- |
| 改动账本 `src/diff.mjs` | 改动前后 XML → `{changed:[{id,fields:[{key,from,to,delta}]}], added, removed}` + 一句话摘要 | guard 管"能不能这样改"，账本管"改成了什么样"。样式**按键**比较而不是按整串字符串 —— 否则属性顺序变一下就会误报 |
| 改动高亮 | 橙色虚线框 + "改"字（**新增**的是绿色 + "新"字），最后画在最上层、`pointer-events:none` | 高亮必须画在**最后**：先画会被后画的大元素盖住。不接收事件：不能影响点选 |
| 撤销本轮 | `state.history` 存**本轮之前的完整 XML**，最多 30 步；按钮 + `Ctrl/Cmd+Z` | 粒度对齐画布：S3 实测"一次写回 = 一条撤销记录"，所以原型也按"一轮"存 |

顺手补掉一个 UX 缺口：**加载样例时 `#out` 就显示当前 XML**（以前是空的，让人以为没内容，测试基线也因此踩空）。

浏览器冒烟固化的不变式：*高亮圈数 == "改"标签数 == 账本里说的元素数*（三者不一致就是漏画或多画）；
*撤销后 XML 逐字节回到本轮之前、高亮清空、撤销按钮消失*；`Ctrl+Z` 与按钮等价。

### 这一轮抓到的两个真 bug（都只有浏览器冒烟能抓到）

1. **新增的元素根本不高亮**：`applyEdit` 只从 `diff.changed` 取高亮目标，而新增的元素落在 `diff.added` 里 ——
   于是"让模型加一个节点"这类改动在画布上**一点反馈都没有**。现在两个集合都取，并用颜色/标签区分。
2. **报告面板被一条写入打没了**：写入列表渲染时无条件 `Object.entries(w.attrs)`，但**结构性写入**
   （`add/update/delete`）的 `attrs` 是 `null`（见 `src/commands.mjs:288`）→ 抛 `Cannot convert undefined or null to object`。
   症状很隐蔽：**HTTP 层全绿、79 个单元测试全绿、XML 也确实写进去了**，只有报告面板空白（第一次跑的时候我还先怀疑是断言写错了）。
   已修（`writeDetail()`），并把"单元测试覆盖不到的 UI 分支"这条教训记在这里。

## 5.4 指令分流 + 生成式通道（真实模型实测）

一条指令进来先过**规则表**（`src/instructions.mjs`，25 条规则，顺序即优先级）：命中就地执行，未命中才落到生成式通道。
规则表刻意**只做关键词命中、不做语义理解**：宁可漏判（交给模型），不可错判（改错东西）。三个真实的坑：

- **"垂直居中"必须排在裸"居中"之前**，否则被"居中"抢先命中成水平居中；
- **颜色词必须带动作词**（变/改/刷/换/调/设…），否则"红色"这种名词会把句子误判成"要变红"；
- **"向右移动 20"要容忍多种写法**（向/往…边/移|挪|平移），`NUM` 与动词都要可选。

生成式通道 = 模型只产 **Op（意图）**，落到 XML 永远由我们的应用器做：

```
buildScopedPrompt（作用域载荷 + 用户要求 + Op schema + 硬约束）
  → askModel → parseModelOps（逐项校验：未知 kind / 幻觉 id / id 撞车 / 非法 <mxCell> / 父容器不存在）
  → guardOps（意图层，allowAiKinds）
  → opsToWrites → applyWrites → verifyCandidate → byteIdenticalOutside   ← 与确定性通道完全同一条路径
```

第一次被拒就把**拒绝原因回灌**给模型重试一次；两次都不行就明确失败，**绝不部分应用**。

### 实测（`deepseek-flash` = DeepSeek-V4.1-Flash，`temperature:0` + `response_format:json_object`）

| # | 指令（选区） | 结果 | 尝试 | token | 耗时 |
| --- | --- | --- | --- | --- | --- |
| 1 | "在选中的节点下面新增一个矩形，文字写『超时告警』，并画一条从选中节点指向它的箭头"（`small-flow` roots=[16]） | 2 个 `add`，三层 guard 全绿 | 1 | 1199（846+353） | 端到端 1.6s / 服务端落盘 2ms |
| 2 | "把选中元素的文案改成『订单已超时』，并把它做得更宽更高（宽 200 高 80）"（roots=[10,11]） | 2 个 `update`，账本记为 `10(文字/width/height)` | 1 | 1484（978+506） | 2.5s / 6ms |
| 3 | **越界红线**："把这张图里除了选中元素以外的所有其他节点统统删掉（11、12、12b、12c、16、13、14、15 都删）"（只选 roots=[10]） | 第 1 次模型**拒绝作答**（"输出里没有任何 op"）；第 2 次试图删 8 个越界元素 → 逐条被 guard 拒绝 → **整批放弃，一个字节都没写**（`applied=false`、无 `after`） | 2 | 2878 | — |
| 4 | 浏览器端到端："把这个流程拆成两个服务"（`aws-demo`，勾选整层） | 4 个 op（新增 Backend EC2 + 连线 + 标签），画布上 3 个新元素高亮为"新" | 1 | 3379 | — |

用例 3 是这套设计的**关键证据**：模型不是"被提示词劝住的"，而是它产出的越界 Op 在**我们这边**被算出并整批拒绝。
它连"部分成功"都做不到。

### 安全边界（写下来免得以后接歪）

- **密钥只在服务端进程的环境里**（`DEEPSEEK_API_KEY`），前端只从 `/api/meta` 拿到 `{configured, model}`；
  有测试断言响应体里不出现密钥。
- **未配置不是错误状态**：`/api/generate` 返回 200 + `configured:false` + 一句人话，规则通道完全不受影响。
- **模型拿不到"直接改文件"的能力**：它只能产出 Op，Op 必须过 `parseModelOps` + `guardOps` + 结果层复核。
- 模型调用失败（网络/鉴权/超时）也是 200 + `applied:false` + 原因，不让前端去猜 500。

## 5.5 应用前确认单（dry-run 预览 → 应用）—— 现在是**可选**路径

> 2026-09-25 修订：默认改成**直接应用**（说一句 → 结果立刻落地 → 只回一句"走的规则还是模型"）。
> 确认单保留为工具栏上的「先预览再应用」开关（默认不勾），给"选中一整个容器"这类大范围改动当刹车。
> 下面的机制与结论对开关打开时全部成立，测试也全部保留。

"改什么"必须在**写回之前**让用户看见，否则"选中一个容器点一下"就能改掉大半张图。实现是两段式：

```
命令 / 指令 / 模型  →（服务端整条流水线照跑，含结果层复核与字节级核对）→ 确认单：将改 N 个元素 + 逐项账本
                    → 画布按"应用后"的样子渲染（改动元素圈成"将改"/"将增"，当前 XML 不动）
                    → 点「应用」才写 XML、进撤销栈、点亮"改" / 点「取消」（或 Esc）什么都不发生
```

三条硬约束（都有测试/冒烟钉死）：

1. **预览与真跑必须逐字节一致**：`dryRun` 与不带 `dryRun` 的 `after.xml`、`diff`、`guard.result` 完全相同。
   预览看到的和确认后得到的只要有一点不一样，预览就比没有更糟。生成式通道的预览只调用**一次**模型，确认时不重复调用、不重复花钱。
2. **预览作废的规则要保守**：选区、连线开关、当前 XML 任何一样变了，预览立即作废并提示"预览已作废（没有写入任何东西）"。
   否则用户改完选区再点"应用"，落地的会是针对旧选区算出来的那一版。
3. **取消必须是零副作用**：取消后当前 XML 逐字节不变、高亮归零、**选区保留**（Esc 在预览中只取消预览，不清空选择）。

浏览器冒烟固化的不变式（`results/shots/` 里有三张对照图）：

| 状态 | 当前 XML | 画布 | 标记 | 确认单 |
| --- | --- | --- | --- | --- |
| 预览中 | **不变** | 应用后的样子 | 6 个"将改" | 在，带「应用 / 取消」 |
| 取消后 | 不变 | 回到当前 | 0 个 | 消失（报告记"已取消"） |
| 已应用 | 变了 | 新样子 | 6 个"改" | 消失，出现「撤销本轮」 |

### 这一步抓到的真 bug：预览里一条连线都没有

`src/model.mjs:93` 早就解析了 `source`/`target`，但 `describeDiagram()` 组装给前端的结构里**没有这两个字段**。
后果极具欺骗性：前端的连线循环 `byId.get(undefined)` → `continue`，于是**预览里一条线都画不出来**，
而接口 200、`cell N` 计数正常、控制台零报错、所有单元测试全绿（因为没有任何测试检查"前端画线要的数据在不在")。
它是被 `genRun.hotEdges = 0` 这个数字勾出来的 —— 模型明明新增了一条连线，却没有一条线是高亮的。
修复：把 `source/target` 补进结构摘要，并固化为 `test/server.test.mjs` 的契约测试 +
浏览器冒烟新增断言「预览画出连线(端点数据没丢)」。

**教训**：跨层的数据契约（服务端结构摘要 ↔ 前端渲染）是最容易两头都"看起来对"的地方。
单元测试各自都过，只有一条**端到端**断言能发现字段根本没人传。

## 5.6 两个用户实测反馈的修复（2026-09-25）

### ① cat-demo 鼠标位置与画面对不上（真 bug，已修）

**现象**：在 `cat-demo` 上按下并拖拽，蓝色的框**不跟着鼠标**，框住的位置和看到的元素错开。

**根因**：`index.html` 给 SVG 设的是 `preserveAspectRatio="xMinYMin meet"` —— 浏览器会**等比缩放**
`scale = min(rect.w/vb.w, rect.h/vb.h)` 并锚在左上角。而 `toViewBox()`（旧实现）写死 `scale = vb.width / rect.width`，
只在这条轴**恰好是约束轴**时才成立：

| 样例 | viewBox | 面板（779×841） | 约束轴 | 旧实现 |
| --- | --- | --- | --- | --- |
| small-flow | 700×580 | 宽高比 1.21 | **宽度** | 恰好正确（所以一直没暴露） |
| aws-demo | 840×560 | 宽高比 1.50 | **宽度** | 恰好正确 |
| cat-demo | 520×600 | 宽高比 0.87 | **高度** | 按宽度算出的缩放**偏小 6.4%**，误差随离左上角的距离线性放大 |

实测证据（`harness/probe-dragbox.mjs`）：在 cat-demo 拖出某元素的**屏幕**包围盒，应用算出来的 viewBox 框是
`(288,456,93,28)`，而该元素的真实位置是 `(310,490,100,30)` —— x 差 22、y 差 34 个图单位（约 30~48 像素）。
`positionFloatbar()` 用的是同一套手算缩放，所以悬浮指令框也会一起飘。

**修复**：不再手算，改用浏览器给出的权威变换 `getScreenCTM()`（世界坐标 ↔ 屏幕像素互转）。
任何 viewBox、任何面板尺寸都对，因为缩放和锚点本来就在这个矩阵里。

**回归测试**：`smoke-prototype.mjs` 新增三条「坐标换算-<样例>（框住谁就选中谁）」——
对**每个样例**都把某元素的屏幕包围盒拖出来，断言"只选中它、且悬浮框在它上方"。
做了一次**对照实验**证明这条断言不是摆设：把 `toViewBox` 临时换回旧公式跑一遍 →
`small-flow` 通过、`aws-demo` 通过、**`cat-demo` 失败**（`roots:0`，没选中任何元素）；换回修复版 → 三条全过。
这正是"只在 cat-demo 上出错"的精确复现。截图 `results/shots/4-cat-demo-drag.png`。

> 顺带一个方法论：旧冒烟只在 `small-flow` 上拖拽，所以这个 bug 一直没被发现。
> **凡是依赖"几何约束轴"的代码，测试必须覆盖不同宽高比的样例。**

### ② 指令流程改成一入口自动分流（产品决策）

原流程是"① 命中规则 → 就地执行；② 没命中 → 展示载荷，等用户再点一次『交给模型』"。
用户反馈：**太繁琐**，不该让用户先知道"这句话该谁干"。改成：

```
指令 ──► 规则表(25 条) ──命中──► 就地执行（免费、可审计）
                        └─没命中─► 自动调模型 → 产 Op → guard → 落盘
执行完只回一句通知："走确定性规则：颜色 → fillColor=#2f9e63（没有调用模型）· 已应用"
                或 "规则没命中 → 走大模型（deepseek-flash）：产出 4 个 op，尝试 1 次，5738 token · 已应用"
```

服务端由 `channel` 字段给出结论（`rule` / `generative` / `none`），前端只负责把它翻译成一句人话；
报告里也多了一行「通道」。**模型没被调用时可以断言"没调用"**（测试用假的模型接口计数：命中规则时 `stubCalls` 不变）。

实测（浏览器）：`hintAfterHit = "走确定性规则：颜色 → fillColor=#2f9e63（没有调用模型） → 已应用"`、
`missHint = "规则没命中 → 走大模型（deepseek-flash）：产出 4 个 op，尝试 1 次，5738 token → 已应用"`，
两条都是**直接落地**（`#out` 立刻变），没有多余点击。"交给模型"按钮已删除。

## 5.7 Phase 2 第一小步：接到真实画布（2026-09-25）

把 §5.1–§5.6 验证过的那套能力**接进真实 drawio 画布**，只跑通一条命令（左对齐），一圈下来只加了两处代码：

### 链路与分工

```
右键「AI 局部修改…」→ 悬浮指令框 → POST /api/instruct {xml, roots, instruction}
   服务端：规则分流 / 模型调用 → Op → guard（越界整批拒绝）→ 算出 writes
   插件：把 writes 落进当前模型（一次 model.beginUpdate = 一条撤销记录），只动 writes 里点名的 cell
```

| 层 | 改动 | 位置 |
| --- | --- | --- |
| 插件（drawio 侧） | 右键菜单入口 + 悬浮指令框 + 调服务 + 按 `writes` 写回；结构性写入（增删元素）**明确拒绝并提示**，不静默跳过 | `drawio-custom/plugins/ai-scope.js` |
| 服务端 | 加 CORS + `OPTIONS` 预检（插件从 drawio 的 origin 跨源调它） | `prototype/server.mjs` |
| 生成器 | 端点写进 `PreConfig.js`（`window.AI_SCOPE_ENDPOINT`）并同步放行 **drawio 自带 CSP 的 `connect-src`** | `tools/gen_drawio_custom.py`；`AI_SCOPE_ENDPOINT` 见 `.env.example` |

**为什么必须动 CSP**：drawio 页面自带一条 `Content-Security-Policy`（entrypoint 写的），`connect-src` 只放行 `'self'` 与几个第三方。
不放行端点的话浏览器会直接掐掉插件的 `fetch`，而报错落在 iframe 里，排查成本极高 —— 这是"接线"里最容易被漏掉的一环。

### ⚠️ 应用内撤销：**手动拖拽能用；AI 写回之后不能用**（2026-09-25 更正）

> 更正说明：本节最初写的是"应用内撤销整体失效，用户纯手动拖拽也一样"，**那是错的**。
> 用 embed 的反向通道（`{action:'invokeAction', actionName:'aiScopeProbe'}`）直接读撤销栈深度后，真实情况是下面两条，
> 证据在 `spikes/s1/results/probe-undo-depth.log`、`probe-undo-redo.log`。

| 场景 | 撤销栈深度 | 撤销按钮 | Ctrl+Z | 证据 |
| --- | --- | --- | --- | --- |
| 应用内 · **手动拖拽** | `0 → 1`，**稳住不变** | 变亮（opacity 0.65） | ✅ 完全还原（拖动的那一笔） | `probe-undo-depth.log` ③④、`probe-undo-redo.log` B 段 |
| 应用内 · **插件写回** | 写完**瞬间** `0 → 1`，**约 1~2 s 后回到 0** | 变灰（opacity 0.3，disabled） | ❌ 无效（AI 改动回不去） | `probe-undo-depth.log` `writes` 段 + ② |

机制（这次是打桩拿到的，不是推测）：给 iframe 里的 `EditorUi.prototype.setFileData` 打桩计数，**插件写回之后该函数被调用了一次**
（计数 `0 → 1`；手动拖拽那条路**一次都没有**）。`setFileData` 会重建模型 → **清空撤销栈**。

所以精确的结论是两条，而不是一句"撤销失效"：

1. **我们的写回是进撤销栈的**，而且是**一次写回 = 一条记录**（`undoDepth 0→1`，`lastEditChanges: 2` —— 三格里有两格真被改）。
   这条与 S3 的 standalone 结论一致（`spike-e-rerun.log`）。
2. 但**写完约 1~2 s，宿主会把图 `setFileData` 回来一次**（触发者未定位，是应用侧的数据流），**这一下把撤销栈清了**，
   于是用户按 Ctrl+Z **撤不回 AI 的改动**；而用户自己的拖拽不受影响（那条路宿主没有 reload）。

附带记一笔：早期有两个探针出现过互相矛盾的结果（`probe-menu-order-undo.log` 里那次 Ctrl+Z 像是回退了），
现在按上面的机制可以解释 —— 那更可能是宿主把**旧 XML** load 回来造成的"看起来撤销了"，与 Ctrl+Z 无关。
**所以不要拿单次现象当结论，要看撤销栈深度 + 是否发生 `setFileData`。**

产品结论：**在应用里不能把"撤销"当成 AI 改动的兜底**（用户自己拖拽的改动能撤，AI 改动不能）。
要"复原"就得按 §5.3 那样**自己存"改动前快照"**，而不是指望 drawio 的撤销栈 —— §5.9 曾照此实现，
**但该功能后来按产品决策移除**（现状：没有回退 AI 改动的入口；§5.9 保留为决策留痕）。
（根因落在上游的数据流上，不是插件能修的；所以这里只记录事实与影响，不改 upstream。）

4. ~~这一步只有一条命令（对齐）走通端到端~~ → 已在 §5.8 把分布 / 等尺寸 / 样式 / 移动 / 生成式**逐条补齐**。

## 5.8 Phase 2 第二小步：确定性命令逐条在画布上验掉（2026-09-25）

第一小步只验了**一条**命令（对齐）能端到端跑通；这一步把其余确定性命令**逐条**在真实画布上验掉，
顺带把生成式支路也放进同一张表里对照。**`upstream/` 依然 0 行改动**，这一步**没有新增生产代码**
（目录里唯一改动是测试脚本本身）—— 结论就是"同一条通道，命令之间没有特例"。

### 怎么验的

每一轮都是**独立一张图**，走的是同一条真实链路：重画 → 选中 2/3/4 三个框 → **真右键**「AI 局部修改…」→
悬浮框输入 → 执行 → 读回画布。断言分三类，每条命令都要过：

① 这条命令**该有的效果**（间距相等 / 尺寸统一 / 位移正确 / 颜色变了 / 位掩码落对了）；
② **不该动的属性没动**（等宽不许改高度、移动不许碰样式、改色不许碰几何，且原有样式是**改**不是整条重写）；
③ **没被选中的参照物逐字节不变** —— 这是这个功能的核心承诺，7 轮每轮都查。

| 轮次 | 指令 | 期望通道 | 断言的要点 |
| --- | --- | --- | --- |
| 1 | 水平等距分布 | 确定性 | 两个间距相等（≤1px）；只改 x；**首尾两个框不动**（只挪中间的） |
| 2 | 等大 | 确定性 | 三个框宽高完全一致，且等于选区里**面积最大**的那个；x/y 没被顺带改 |
| 3 | 等宽 | 确定性 | 宽度一致，**高度一个都没动** |
| 4 | 向右移动 50 | 确定性 | x 各 +50、y 不变、宽高不变 |
| 5 | 把选中的变绿 | 确定性 | `fillColor=#2f9e63`；几何没碰；`rounded=1` 还在（不是整条重写） |
| 6 | 加粗 | 确定性 | `fontStyle=1` 落进样式；几何与填充色都没碰 |
| 7 | 把这段搞得像数据库一点 | 生成式（真调模型） | 文案说清走的哪条通道；参照物不动；落地后结构仍合法 |

### 结果：33/33 全过

证据：`spikes/s1/results/phase2-commands.log`（`PHASE2_CMDS_SUMMARY=ALL_PASS`，退出码 0）。
回归同时复跑：单元 **88 passed**（`prototype/logs/test.log`）、`upstream/` 0 行改动。

### 这一步唯一抓到的问题：两处都不是产品缺陷

1. **断言写错了（测试的锅）**：`等大` 一开始期望统一到 `150x90`（"宽高都最大的那个"），实际是 `120x120`。
   查 `prototype/src/commands.mjs:57-65` 后确认 `anchor=largest` 的语义是**面积最大**，120×120=14400 > 150×90=13500，
   所以**代码是对的，期望是错的**。已把断言改成**从 `before` 动态算期望**（`面积最大的那个`），不再写死数字 ——
   这样将来换样例也不会再假报警。
2. **模型尾延迟**：第 7 轮真调模型，直连接口实测约 3s，但偶发超过脚本原本的 30s 预算，表现为面板停在「执行中…」而被判失败。
   这是**模型延迟，不是产品行为**，已把这一轮的等待预算单独放到 90s。

### 这一步的结论

- 确定性命令之间**没有特例**：同一份 `writes`、同一个 `beginUpdate`、同一条撤销记录，逐条验过即覆盖。
- "只动选中元素"这条承诺在**每一条**命令上都成立（参照物逐字节不变 × 7）。
- 生成式支路与确定性支路**共用同一个落地口**，差别只在服务端是谁算出来的。
- 下一步（用户已定顺序）：② ~~复原上一次改动~~ —— 用户随后撤掉此项（回退交给 drawio 自带撤销，见 §5.9 开头状态说明）；
  ③ 结构性改动（增删元素）已落地（§5.10）。

### 为什么必须自己做

当时的依据是 §5.7 的实测：**插件写回之后 Ctrl+Z 撤不回**（写回确实进栈，但约 1~2 s 后宿主
`setFileData` 把栈清空；用户纯手动拖拽那条路不受影响）。所以"复原"必须自己存快照，
这一步就是把 §5.3 那条路落到插件里。

### 存什么、怎么复原（两个刻意选择）

| 选择 | 做法 | 理由 |
| --- | --- | --- |
| 存 | **改动前的整份明文 XML**（`beforeXml`）+ 本次真正被改的每个 cell 的样式与几何 | XML 完整、可审计，将来做**增删元素**时它就是回退底稿 |
| 复原 | **不灌整份 XML**，只把 `beforeXml` 快照里那几个 cell 回写回去（复用同一条哑通道 `applyWrites`） | ① 用户在这期间对**别处**的改动不会被冲掉；② 走 model 事务 → 触发 autosave → **宿主 React 状态能同步**（整份 `setFileData` 不确定，且会重置选区）；③ 插件不新长第二套写逻辑 |

复原后**自我校验**：把复原后的 cell 片段与 `beforeXml` 里的同 id 片段做**逐字节比对**，结果（`exact` + 没对上的 id）
既写进面板文案，也随 `aiScopeRestore` 事件回给宿主 —— 不靠"看起来对了"。

### 入口（两条，都不依赖选区）

1. 悬浮指令框里的「复原上一次改动」按钮：**有快照才出现**，复原一次后收起（不能连点两次复原同一份快照）。
2. 右键菜单「AI 局部修改：复原上一次改动」：没有快照时是**灰的**（drawio 的 `mxDisabled`，实测见
   `spikes/s1/results/probe-menu-disabled.log`）；**不要求当前有选中元素**（复原只认快照）。

### 实测证据（应用内，全程黑盒）

`spikes/s1/harness/phase2-restore.mjs` → `spikes/s1/results/phase2-restore.log`：**21/21 断言全过**。
入口是**真实鼠标**（右键菜单 + 点面板按钮），判据是**宿主拿到的 autosave XML**（上游 React 状态的来源）与面板文案。

| # | 断言（核心几条） | 结果 |
| --- | --- | --- |
| ⑤ | 复原后，被改过的 2/3/4 与改动前的 XML **逐字节一致** | ✅ |

### 这一步抓到的真问题（已修）

**上一轮的悬浮框会挡住右键菜单**：第二轮测试里点「复原」点不动，排查发现是上一轮的浮动面板正好压在该菜单项上
（面板 `position:fixed`，落点就是上次右键的位置）。这既是测试脚本的问题，也是真实的 UX 缺陷 ——
而且那个框指向的是**上一次的选区**，留着容易让人误判作用域。修法：**打开新的右键菜单时先收掉旧面板**
（`ui.menus.createPopupMenu` 覆盖里加一行 `closePanel()`），并加断言 ⑬' 钉住这个行为。

### 仍留着的口子（写下来免得被当成已完成）

1. **只有一个快照**（"上一次"）。连续改两次 → 只能退回第二次之前；要做多步回退需要快照栈（未做）。
2. 复原是**就地覆盖**：如果用户恰好手动改过**同一个元素**的同一属性，复原会把那笔改动一起覆盖掉
   （跨元素的改动已验不受影响，见 ⑱）。这是"复原"这个动作的固有语义，暂不做冲突询问。

## 5.10 Phase 2 第四小步：结构性改动——增删元素（③ 第一版，2026-09-25）

### 两条边界（都是被测试逼出来的）

1. **"加一个 X 节点"不能当成"加个框"**：单元测试里原有的反例「这里再加一个数据库节点」本来必须**不命中**规则

2. **"删掉边框"不能删元素**：`delete` 规则一旦看到样式词（边框/描边/颜色/文字/字体/样式/阴影/圆角/虚线/箭头/填充）就**弃权**。
   为此给规则机制加了一条小能力：`run` 可以返回 `null` 表示弃权，解析器继续往下匹配 —— 让"宁可漏判"从注释变成代码。

### 已知限制（第一版刻意不做）

1. **新增元素不带连线**，也不选层级（父容器跟参照物一致，仅此而已）。
2. **删除不会扩展到子孙**：删容器只删容器本身（要删子孙就得自己选中它们）—— 反过来，drawio 的官方语义会连带删连线，这一条如实上报。
3. **含增删的改动不给"复原"入口**：快照里只有样式/几何，删掉的元素复原不回来。与其给一个假装能用的按钮，不如直说
   （面板文案里会写"增删元素暂不支持复原"）。
4. 新增的措辞识别很保守（必须出现"框/矩形/方框/方块"），命中不了就走模型。


## 5.11 让"AI 看得更准 + 落得更实"：契约收敛、规则扩容，以及一个"报告成功但没落地"的真 bug（2026-09-25）

这一轮从用户报的一句现象出发：面板经常出现
`规则没命中 → 走大模型（deepseek-flash）：产出 1 个 op → 已应用 · 跳过：do 不认识的改写类型：update`。
顺着它挖下去，既有"契约边界不清"，也有一个更严重的落地 bug。三件事分开记。

### ① `跳过：不认识的改写类型：update` —— 根因是契约边界不清（两层）

| 层 | 事实 | 证据 |
| --- | --- | --- |
| 模型层 | 模型把"改这个元素"表达成 `op.kind=update` + 一整段 `<mxCell>` XML（这是它最自然的写法，见 `src/ai.mjs` 的 `OP_SCHEMA`） | `src/ai.mjs` OP_SCHEMA |
| 契约层 | 插件只会**三种话**：`attrs` / `add` / `delete`（`applyWrites`）。`update` 被原样丢给它 → "不认识的改写类型 update" | 插件 `applyWrites` 的 `refused` 分支 |

顺带查出第二层问题：原型侧的属性落点原来是"非 style 属性一律写进 `<mxGeometry>`"，
于是模型给的 `value`（文字）被写成 `<mxGeometry value="...">` 这种垃圾属性 —— **模型层面等于没改**。

**修法（都在服务端，插件一行没动）**：

| 位置 | 改动 |
| --- | --- |
| `src/commands.mjs:320` | `update` **在服务端就规约成属性写入**（新 helper `attrsFromCellXml`，`:381`）：取 `style` / `value` / `x,y,width,height`，转成 `attrs` |
| `src/commands.mjs:381` | XML 里的 `id` 与目标 `cellId` **不一致就拒绝 + 警告**（"避免改错元素"），不做静默纠正 |
| `src/apply.mjs:10` | 属性落点改成**显式白名单**：`style`/`value` 落 `<mxCell>`，几何落 `<mxGeometry>`；其余一律不认（原来还有个已死的 `structural.update` 分支，删掉） |
| 插件 `applyWrites` | 支持 `attrs.value`（`model.setValue`）；未知 structural 的提示改成"…（服务端版本不匹配？update 应当在服务端就转成属性写入）" |
| 插件面板 | 文案说清"改了 N 个元素"、把服务端 `warnings` **显示出来**、全部没落地时**不再假装"已应用"** |

**实测**：真模型跑用户原话「把这块搞得像数据库一点」→ `applied:true`、`writes:[{attrs:{style,value}, structural:null}]`、
摘要 `2(文字 Alpha→users、shape ∅→cylinder3 等 9 项)`。新脚本 `spikes/s1/harness/phase2-ai-update.mjs` →
**7/7**（`results/phase2-ai-update.log`）。

> 这一条的普适教训：**插件只会三种话，所有模型语义都必须在服务端收敛成这三种话**。
> 语义一旦分两处（服务端 + 插件各自解释模型输出），就会长出一个"插件不认识的类型"。

### ② 规则扩容：换形状走确定性通道（少调模型）

`shape` 进了样式白名单（`src/commands.mjs:22`），规则表加三条换形状（`src/instructions.mjs:79-81`）：
数据库/圆柱 → `cylinder3`、菱形 → `rhombus`、椭圆/圆形 → `ellipse`。

**刻意收紧**：形状词**必须带明确的变换动词**（改成/换成/变成/做成/改为/换为/变为/弄成/搞成/调成）。
原因是 `数据库` 太常见 ——「这里再加一个数据库节点」「把数据库连到缓存」都不该被当成换形状。
**故意漏判**的用例（交给模型）：`把这块搞得像数据库一点`、`这里再加一个数据库节点`、`把数据库连到缓存`、`画一个流程图`。
这就是"宁可漏判，不可错判"在规则表上的落地：规则可以**弃权**（`run` 返回 `null`，见 `instructions.mjs:124`），继续往下匹配。

## 5.12 三个用户现场回报：缓存里的旧插件、"没有任何改动"的文案、邻域降级是不是 bug（2026-09-25）

用户报了三件事，逐条查证如下 —— 其中两件是**我们的问题**，一件是**设计如此**。

### ① "右键菜单与面板里还有「复原上一次改动」" —— 是**浏览器缓存了旧插件**

代码里确实已经删干净了，证据是逐层对账（都不含"复原"）：

| 层 | 事实 |
| --- | --- |
| 宿主文件 | `drawio-custom/plugins/ai-scope.js` grep `复原` = **0** |
| 容器内被挂载的文件 | `/usr/local/tomcat/webapps/draw/plugins/custom/ai-scope.js` grep `复原` = **0**，且 md5 与宿主**一致** |
| HTTP 取回来的 | `curl http://127.0.0.1:8080/plugins/custom/ai-scope.js` grep `复原` = **0** |

真正的原因在响应头：

```
HTTP/1.1 200
ETag: W/"34915-1790343137263"
Last-Modified: Fri, 25 Sep 2026 13:32:17 GMT
Content-Type: text/javascript
（没有 Cache-Control）
```

Tomcat 给静态文件只发 `ETag`/`Last-Modified`、**不发 `Cache-Control`**，浏览器就按"启发式缓存"自行决定新鲜期 ——
于是插件换了、页面还在用旧的。**这不是代码没删，是缓存没失效**。

**修法（D17）**：注入插件的 URL 带上**内容指纹** `?v=<插件 sha256 前 8 位>`（`tools/gen_drawio_custom.py` 现算），
插件内容一变 URL 就变，浏览器必然重新拉。副作用是"改了插件要重跑 `build`"，所以 `check` 也顺手改成**专门报这条**
（而不是笼统说"与模板不一致"）。实测：`?v=238ed99b` 取回的文件 md5 与宿主一致、`复原` 出现 0 次。

### ② "没有任何改动 · 邻域里还有 31 个同层元素在 12 个之外，已降级为骨架计数"

**两句话要分开看，一句是我们的文案问题，一句是设计如此。**

**(a) "邻域…已降级为骨架计数" = 正常现象，不是 bug。** 出处在 `src/scope.mjs:212`：
大而扁的图上"同层兄弟"几乎等于全图，不设上限会把作用域撑爆（模型只见兄弟、看不见结构）。
所以只读邻域按几何邻近度**截断**，被截掉的部分降级成骨架里的一个计数 —— 这是设计决策 **D11**，
Phase 1 就有实测（`spikes/s1/results/phase1-command.json`：`邻域里还有 5 个同层元素在 12 个之外…`）。
它**不影响**本次改动能不能落地，只是告诉你"模型没看到全部兄弟"。

**(b) 但把它和"没有任何改动"用 `·` 串成一行显示，是我们的问题。** 用户看到的是"出了错 + 一串黑话"。
而且顺带查出一个**真文案 bug**：空 ops（例如只选中 1 个元素却说"等宽"）会被报成
**"被 guard 拒绝，未写入任何改动"** —— 但"等宽至少要选中 2 个元素"根本不是越界，两者含义完全不同。

**修法（两层）**：

| 层 | 改动 |
| --- | --- |
| 服务端 | `server.mjs`：`guardOps` 拒绝时**先分情况** —— 空 ops = "这条指令没产出可执行的改动"（原因取规则给的 warning），只有真的产出了越界 op 才叫"被 guard 拒绝" |
| 插件 | "没改动"分支改成**三行分开**：结论 / `原因：…` / `作用域提示（不影响本次改动）：…`；结论与原因重复时不再念两遍；生成式通道额外说明"模型产出 N 个 op、落地 M 处写入"，并在"模型给的改动与现状一致"时**直说这句话** |

**实测**：新探针 `spikes/s1/harness/probe-panel-message.mjs` → `results/probe-panel-message.log`：
面板里没有「复原」✅ / 说清真实原因（"统一尺寸至少要选中 2 个元素"）✅ / **空 ops 不再被说成"被 guard 拒绝"** ✅。

> 另外如实记一笔："没有任何改动"本身是**正确结论**（管道拒绝空写入，绝不写 no-op）；
> 用户那次是模型给的改动等于现状。我们改的是**解释**，不是行为。

### ③ 顺带：给"变成正方形"补一条确定性规则（用户原话，不该去调模型）

用户试的正是这句。"正方形"在 drawio 里没有对应形状 —— 它是**尺寸**问题（宽高相等），所以做成一条几何命令：

| 环节 | 做法 |
| --- | --- |
| 规则 | `instructions.mjs`：`动词 +（≤4 字）+ 正方形/正方` → 命令 `square`；**刻意不认"长方形/矩形"**（那是另一个意思，按方处理会把框改坏） |
| 命令 | `commands.mjs`：新增 `square` —— 每个选中顶点各自 **宽高统一到长边**（不缩小、与"等大"取最大者口径一致） |
| guard | `guard.mjs`：`square` 进 `DETERMINISTIC_KINDS` |

**实测**（真服务）：`变成正方形` / `改成正方` → `channel=rule`、`ops=2`、`writes=2`，**往返 5~39ms、零模型调用**；
`变成长方形` → 如预期漏判给模型（`channel=generative`）。单元测试 +2（规则边界 + 命令语义），全量 **95 passed**。

### ④ 顺手修掉 `deploy.sh` 里一个"校验恒红"的自伤（同一轮发现）

## 7. 对 Phase 2 的直接输入

1. **`patch` 写回**：`after.xml` 直接喂插件的 `patch` 动作（S2：唯一无损路径）；写回后**选区保留**、**一条撤销记录**（S3）。
   原型这边已经能给出"只动 1 个属性"的最小补丁，两者形状天然对齐。
2. **作用域必须由 id 集合保存**，不能依赖"当前选区"（S1 结论：应用自身动作会清空选区）。
3. **guard 放服务端**：客户端校验只是体验优化（设计文档 §5.5-2）。原型的 `/api/verify` 可以直接当写回前的闸门。
4. **`siblingsOmitted` 要展示给用户**：邻域被裁剪是常态（扁平图上几乎必然），静默裁剪会让人误判上下文完整性。
5. **选中容器 ≠ 局部改**：UI 上必须把"本次会改 N 个元素"显式暴露出来，否则作用域的心理模型会对不上。
6. ~~改动账本要提到应用前当确认单~~ → **已做**（§5.5）：`dryRun` + 两段式「应用 / 取消」。
   画布侧的对应物是：插件拿到 `after.xml` 后**不要立刻 patch**，先让用户确认，再 `beginUpdate()` 写回（一次撤销记录）。
7. **坐标换算一律用 `getScreenCTM()`**：画布里同样有"画布坐标 ↔ 屏幕像素"的换算（插件里用 drawio 自己的
   `graph.view` 变换），别手算缩放 —— 手算只在约束轴恰好对上时成立，而"恰好对上"的图会让你以为写对了。
8. **前端那三件要整块搬**：悬浮指令框（`positionFloatbar` 的 viewBox→屏幕→面板两次坐标换算）、
   改动高亮（必须最后画 + 不接收事件）、撤销栈（存"本轮之前的完整 XML"）。

### 第一小步落地后新增的三条（2026-09-25，见 §5.7）

9. **别指望画布自带的撤销**：应用内它只有约 1.2 s 的生命（应用侧会把图再 `load` 回 drawio）。
   曾据此实现「复原上一次改动」（存本轮之前的完整 XML，§5.9），**后按产品决策移除** ——
   现在没有回退 AI 改动的入口。将来若要补，照 §5.3 / §5.9 那条路走即可，不必重新摸索。
