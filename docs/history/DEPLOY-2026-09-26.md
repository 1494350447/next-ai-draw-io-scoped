# 历史部署说明（2026-09-26，当前说明见根目录 DEPLOY.md）

用聊天生成 / 修改 draw.io 图表的自建服务。本目录是一层薄薄的编排覆盖层，上游代码原样复用，
不改上游任何文件。

- 部署方式：Docker Compose（复用上游 `docker-compose.yml` + 本目录覆盖层）
- 上游版本：`DayuanJiang/next-ai-draw-io` @ `027cd88`（2026-09-01）
- 本机实测：Ubuntu 24.04 / Docker 29.1.3 / Compose 2.40.3，部署已跑通

## 前置条件

| 项 | 要求 | 说明 |
| --- | --- | --- |
| Docker | 24+ 且当前用户在 `docker` 组 | `./deploy.sh doctor` 会检查 |
| Compose | v2（`docker compose` 子命令） | 需要支持 `!override` 标签，2.24+ 均可 |
| 磁盘 | 约 3 GB | 应用镜像 351 MB + drawio 1.35 GB + 构建缓存 |
| 端口 | 宿主 `3000`、`8080` 空闲 | 想在别的端口上跑见 FAQ |
| 出网 | 能访问 npm 镜像源与 `api.deepseek.com` | 构建已固定走 `registry.npmmirror.com` |

## 部署步骤

```bash
cd ~/deploy/next-ai-draw-io

# 1. 填密钥（.env 已经建好，权限 600；只需确认 DEEPSEEK_API_KEY 是你要用的那把）
$EDITOR .env

# 2. 体检：docker 权限、端口、上游 checkout、覆盖层一致性、必填变量
./deploy.sh doctor

# 3. 构建镜像（首次约 2 分钟：1459 个依赖 + next build）
./deploy.sh install

# 4. 启动并等就绪
./deploy.sh up

# 5. 完整闭环：就绪 + 幂等 + 真的调一次模型 + 停止清理检查 + 重新拉起
./deploy.sh verify
```

## 配置项

改 `.env` 后需要 `./deploy.sh up` 让容器重读（`env_file` 是启动时注入的）。

| 变量 | 必填 | 出处 | 说明 |
| --- | --- | --- | --- |
| `AI_PROVIDER` | 是 | `upstream/lib/ai-providers.ts:748` | 当前 `deepseek` |
| `AI_MODEL` | 是 | `upstream/lib/ai-providers.ts:740` | 当前 `deepseek-flash`（= DeepSeek-V4.1-Flash） |
| `DEEPSEEK_API_KEY` | 是 | `upstream/lib/ai-providers.ts:1072` | 服务端调模型用的 key |
| `DEEPSEEK_BASE_URL` | 否 | `upstream/lib/ai-providers.ts:1075` | 留空 = 官方 `https://api.deepseek.com/v1` |
| `ACCESS_CODE_LIST` | 否 | `upstream/app/api/chat/route.ts:83` | 逗号分隔的访问码；填了前端必须输入其一 |
| `ADMIN_PASSWORD` | 否 | `upstream/docs/cn/admin-panel.md:7` | 留空 = `/admin` 面板关闭；填了才开放 |
| `AI_SCOPE_ENDPOINT` | 否 | `tools/gen_drawio_custom.py`（读 `.env`） | **局部编辑 API**端点，默认 `http://localhost:3000`。drawio 插件把「选中元素 + 一句指令」POST 到 next-ai-draw-io 的 `/api/scoped-edit`；**构建期**变量：改完要重跑 `python3 tools/gen_drawio_custom.py build` 并重启 drawio 容器 |

换 provider 只要改这三个值并 `./deploy.sh up`（无需重新构建，provider 是运行时读的）：
例如 `AI_PROVIDER=openai`、`AI_MODEL=gpt-4o`、`OPENAI_API_KEY=...`。可用 provider 见
`upstream/lib/ai-providers.ts:690` 附近的注释。

## drawio 定制（插件挂载）

这个部署**改了一处 drawio**：往编辑器里挂了一个适配插件。它做两件事：读选区并回传宿主；
在右键菜单里提供「AI 局部修改…」（**紧跟在官方「删除」下面，绿色字体**）——选中元素 → 悬浮指令框 → 调 next-ai-draw-io `/api/scoped-edit` → **只改选中的元素**
（对齐/分布/等尺寸/改色之类的属性改动，以及**选中后的局部增删**："删掉选中的"、"在旁边加一个同色圆角框"）。
draw.io 侧通过 compose 只读挂载插件；局部编辑 API 已合并到 `upstream/` 的 next-ai-draw-io 服务，复用它的模型调用链路。

> 历史上还做过一条「AI 局部修改：复原上一次改动」（自存改动前快照、不依赖 drawio 撤销栈），
> **后按产品决策移除**：用户判断"回退上一次"应由 drawio 自带的撤销承担，面板里再挂一个同类入口是重复。
> 注意这是产品取舍，不等于应用内撤销可用 —— 实测结论（AI 写回后 Ctrl+Z 撤不回）仍记在
> `prototype/RESULT.md` §5.7 与 `docs/scoped-editing-design.md` 附录 F.4。

| 挂载 | 容器内路径 | 作用 |
| --- | --- | --- |
| `./drawio-custom/PreConfig.js` | `/usr/local/tomcat/webapps/draw/js/PreConfig.js` | drawio 官方留给自托管的定制入口，在应用脚本之前执行：设 CSP（含放行 `AI_SCOPE_ENDPOINT` 的 `connect-src`）、写 `DRAWIO_*` 与 `window.AI_SCOPE_ENDPOINT`、**注入下面的插件** |
| `./drawio-custom/plugins` | `/usr/local/tomcat/webapps/draw/plugins/custom` | 插件目录。挂 `plugins/` 的**子目录**是必须的：直挂 `plugins/` 会盖掉镜像自带的 22 个官方插件 |

**插件的缓存失效靠内容指纹**：注入的 URL 是 `/plugins/custom/ai-scope.js?v=<插件 sha256 前 8 位>`。
起因是一次实测事故 —— 代码里已经删掉的功能，在用户浏览器里"还在"：Tomcat 对静态文件只发
`ETag`/`Last-Modified`、**不发 `Cache-Control`**，浏览器按启发式缓存继续用旧插件。
所以**改完插件要重跑 `python3 tools/gen_drawio_custom.py build`**（换指纹）；忘了跑，
`python3 tools/gen_drawio_custom.py check`（`deploy.sh doctor` 里也会跑）会专门报"插件指纹不是当前的"。

**为什么必须用只读挂载**：镜像的 `/docker-entrypoint.sh` 每次容器启动都会**重写** `js/PreConfig.js`
（`echo … > $CATALINA_HOME/webapps/draw/js/PreConfig.js`）。所以"用 `docker cp` 把定制版塞进去"只在当次运行有效，
**重启就没了**。只读挂载顶掉它，才做到"重启/重建后仍在"。

**代价（实测，会看到一条 WARNING）**：entrypoint 开头用 `touch PreConfig.js` 探测写权限，只读挂载让它失败，
于是它打印下面这行后直接启动 Tomcat，**跳过整段运行时改写**：

```
WARNING: No write access to /usr/local/tomcat (running as UID 1001, GID 999).
         Skipping runtime configuration: DRAWIO_* environment variables, SSL and the
         context path will NOT be applied.
```

被跳过的内容以及影响：

| 被跳过 | 影响 |
| --- | --- |
| CSP meta、`DRAWIO_*`、`urlParams['db'|'gh'|...]='0'` | **无影响** —— 等价内容已在 `drawio-custom/PreConfig.js` 里静态化。`DRAWIO_BASE_URL` 改为从 PreConfig 自身 `<script src>` 反推部署前缀，所以 `/`、`/draw/`、反代子路径都成立，也不再依赖环境变量 |
| SSL 自签证书 / 8443 端口 | **无影响** —— 只跑 8080 明文 |
| Tomcat 子路径 context 重写 | **无影响** —— 不用子路径（若将来要给 drawio 配子路径，需改用入口页 URL 与 PreConfig 对齐后再验证） |
| `PostConfig.js` 追加的 3 行（`EditorUi.enableLogging=false`、`isDriveDomain`） | 可忽略 —— 自托管下不涉及 Drive 集成；日志上报本来也会被 CSP 挡住 |

**怎么验证**：

```bash
./deploy.sh plugin-check     # 当前容器 → restart 后 → --force-recreate 后，三次都校验一遍
./deploy.sh doctor           # 顺带校验定制资产自洽、docker-compose.yml 没被手改
```

**升级 drawio 镜像后**（`jgraph/drawio:latest` 变了）要重新探测一次，让 `.orig` 与锁文件跟新镜像对齐：

```bash
docker compose pull drawio && python3 tools/gen_drawio_custom.py probe && ./deploy.sh plugin-check
```

### 「AI 局部修改…」要能用的两个前提

右键菜单点开悬浮框之后，插件会去调 `AI_SCOPE_ENDPOINT`。要真能改图，需要：

1. **next-ai-draw-io 应用在跑**：执行 `./deploy.sh up` 会启动并检查 `GET /api/config`；局部编辑接口与主聊天共用同一应用、模型配置和密钥。`prototype/` 只作为零依赖回归工具保留，不参与生产请求。
2. **浏览器能放行它**：插件的 fetch 受 drawio 页面自带 CSP 的 `connect-src` 约束，这一条由
   `tools/gen_drawio_custom.py` 按 `AI_SCOPE_ENDPOINT` 的 origin 自动生成 —— 所以改了端点必须重新 `build`
   并重启 drawio 容器，否则报错只会出现在 iframe 的控制台里，很难查。
   另外这个地址必须是**浏览器**能访问到的（不是容器间可达地址）：默认 `localhost:3000` 只适用于浏览器就在这台机器上。

**这一步的实际边界**：服务端复用上游 `edit_diagram` 的 `update/add/delete` 协议，并以 `selectedIds` 做强 guard；插件使用 mxGraph 官方事务 API 写回，属性写入与结构性增删都只作用于允许范围。
另外**不要指望用 Ctrl+Z 撤销应用里的改动**：应用侧在画布变更后会把图再 load 回 drawio，而 embed 的 load 会重置撤销栈
（用户自己手动拖拽也一样；实测见 `prototype/RESULT.md` §5.7）。

**改定制本体**：改 `tools/gen_drawio_custom.py` 里的模板（或 `drawio-custom/plugins/ai-scope.js`），然后
`python3 tools/gen_drawio_custom.py build && python3 tools/gen-override.py`，再 `./deploy.sh up`。
`drawio-custom/PreConfig.js` 是生成物，不要手改。

**想关掉这个定制**（回到原版 drawio）：把 `tools/gen_drawio_custom.py` 里 `DRAWIO_SECTION` 的 `volumes` 去掉后重跑
`gen-override.py`，或临时用 `./deploy.sh` 之外的方式起容器（`docker compose -f upstream/docker-compose.yml up -d`）。

## 运维要点

**升级上游代码**

```bash
git -C upstream pull --ff-only
python3 tools/gen-override.py     # 上游 Dockerfile 变了就必须重跑
./deploy.sh install && ./deploy.sh up
```

`./deploy.sh doctor` 会比对覆盖层里的 Dockerfile 与上游 `upstream/Dockerfile`：上游一改就会
提示漂移，此时必须重跑 `gen-override.py` 并复核差异，否则构建用的是过期的 Dockerfile。

**让局域网里其他机器访问**

构建期会把 drawio 地址写进前端 bundle。默认是 `http://localhost:8080`，只对"浏览器就跑在
这台机器上"成立。要让同网段其它机器访问，用宿主 IP 重新构建：

```bash
DRAWIO_PUBLIC_URL=http://192.168.1.50:8080 ./deploy.sh install
./deploy.sh up
```

（已实测：换地址会产出新的前端 chunk，恢复默认后旧地址不再出现。改成宿主实际 IP。）

**data/ 写权限**

`data/` 由 compose 以 `root:root 755` 创建，容器进程是 `uid 1001`。读不到 `settings.json`
是正常的（缺失被忽略），应用运行和聊天都不受影响；只有启用 `ADMIN_PASSWORD` 后台面板并
保存设置时才会写失败。启用前先：

```bash
sudo chown -R 1001:1001 ~/deploy/next-ai-draw-io/data
```

**彻底卸载**

```bash
./deploy.sh reset --purge
docker image rm next-ai-draw-io-next-ai-draw-io:latest jgraph/drawio:latest
docker builder prune          # 清掉构建缓存（本机约 4.8 GB，含其他项目的缓存，按需）
```

## 常见问题

**Q：改了 `.env` 为什么没生效？**
A：`env_file` 只在容器启动时注入。跑 `./deploy.sh up` 重建容器。`AI_PROVIDER/AI_MODEL` 是
运行时读的，改完 `up` 即可；`NEXT_PUBLIC_*` 是**构建期**变量，改完必须 `./deploy.sh install`。

**Q：端口被占用。**
A：上游 compose 把端口写死成 `3000:3000` / `8080:8080`，本覆盖层故意不重复声明 ports——
compose 对 ports 是"拼接"语义，重复声明会让同一宿主端口绑定两次并直接报错。
需要换端口时另加一份文件（**这条未实测**，仅作为方向）：

```yaml
# docker-compose.ports.yml
services:
  next-ai-draw-io:
    ports: !override ["13000:3000"]
  drawio:
    ports: !override ["18080:8080"]
```

然后 `docker compose -f upstream/docker-compose.yml -f docker-compose.yml -f docker-compose.ports.yml up -d`。
注意换了 drawio 宿主端口后，`DRAWIO_PUBLIC_URL` 也要跟着改并重新 `install`。

**Q：drawio 日志开头那条 `WARNING: No write access to /usr/local/tomcat` 要紧吗？**
A：是预期行为，不是故障。它的意思是 entrypoint 放弃了运行时改写（`DRAWIO_*` 环境变量、SSL、子路径、
`PostConfig.js` 追加），因为 `PreConfig.js` 被我们**只读挂载**顶掉了 —— 这正是"重启/重建后插件仍在"的代价，
等价内容已静态化进 `drawio-custom/PreConfig.js`。细节与逐项影响见上面「drawio 定制」一节。
反过来说：**如果哪天这条 WARNING 消失了**，说明挂载没生效（插件也随之失效），跑 `./deploy.sh plugin-check` 确认。

**Q：怎么确认 drawio 定制还活着？**
A：`./deploy.sh plugin-check`。它会校验"容器内文件与工作目录同源 + HTTP 能取到注入标记与插件 +
官方插件没被盖掉"，并在 `restart` 与 `--force-recreate` 之后各验一次。打开 drawio 后如果适配层加载成功，
浏览器控制台不会有插件相关报错，页面上右键任意元素能看到多出来的一条菜单项：「AI 局部修改…」
（不选中任何元素时它是灰的）。

**Q：聊天报错 / 模型不可用。**
A：先 `./deploy.sh smoke` 看真实报错；再查 key 余额、`AI_MODEL` 是否是 provider 侧真实存在的
模型 ID（DeepSeek 用 `GET https://api.deepseek.com/models` 核对）、容器能否出网。

**Q：`/admin` 打不开。**
A：`ADMIN_PASSWORD` 为空时面板整个禁用，这是默认行为。

**Q：构建很慢或者卡在 npm。**
A：构建已固定 `registry.npmmirror.com`，用 `grep -o 'https://registry\.[a-z.]*' logs/build.log | sort | uniq -c`
确认。若走了官方源说明覆盖层被改坏了，重跑 `python3 tools/gen-override.py`。
